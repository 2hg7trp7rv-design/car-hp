# GUIDE / COLUMN 記事制作ルール

このファイルは、CAR BOUTIQUE JOURNAL の Guide / Column 記事を作るときの固定ルールです。

対象は `data/articles/guides/*.json` と `data/articles/columns/*.json` の全記事です。

既存記事の修正、新規記事の作成、画像追加、表・カード追加、関連記事導線の調整は、必ずこのルールに従います。


---

## 0. CBJ作業前の強制チェック

CBJで記事作成、リライト、画像追加、CSS修正、SEO確認、ZIP納品を行う前に、必ず以下を確認します。

```txt
1. 最新リポジトリZIPを確認する。
2. 対象JSONを確認する。
3. 表示コンポーネントを確認する。
4. 共通CSSを確認する。
5. 画像パスと public-assets を確認する。
6. sitemap / robots / audit / prebuild の状態を確認する。
7. 親記事と子記事の役割を比較する。
8. PDF・スクショ・実機表示とコード上の想定を照合する。
9. 実機未確認なら、実機確認済みのように断定しない。
10. 根拠を示してOK / NGを判断する。
11. 親記事と子記事で、タイトル、章タイトル、本文、カード、表、画像まわりの共通デザインルールが揃っているか確認する。
12. 記事内画像と一覧画像の役割、挿入位置、画像パス、public-assets登録、スマホ可読性、OGP fallbackの有無を確認する。
```

記事ごとに内容の深さ、各章ごとのボリューム、カードの数、カードの配置、表の数、画像の数、画像の挿入位置は違ってよいです。

ただし、タイトル、各章タイトル、本文の文字サイズ、行間、カードの色、カードの角丸、カードの影、表、NG / OKカード、画像キャプションの基本デザインは、親記事と同じ共通CSSのルールに揃えます。

一覧画像は記事テーマを一目で伝えるための専用KVです。
本文内の説明図と混ぜません。
一覧画像には記事タイトルや長文を入れません。

## 1. Guide と Column の役割

### Guide

Guide は、読者が実際に迷ったときに使う実用記事です。

トップ説明文は次で固定します。

```txt
車選びや整備、カスタムで迷ったときに見る実用記事
```

Guide に入れるテーマは、原因、確認方法、選び方、費用、手順、比較、失敗回避などです。

読後に、読者が何を確認し、どう判断すればよいかが分かる状態にします。

### Column

Column は、実用記事だけでは拾いきれない背景、考え方、見方を扱う記事です。

トップ説明文は次で固定します。

```txt
車選びや維持費、カスタムの考え方を、少し深く読み解く記事
```

Column は感想文ではありません。

Guide ほど手順化しすぎず、ただの抽象論にも逃げず、読者の見方が変わる深さを持たせます。

## 2. 文章の基本ルール

### 2-1. 句点ごとの改行

日本語の表示文は、原則として句点「。」ごとに改行します。

これは本文だけではなく、タイトル、リード、キャプション、FAQ、表の説明、カード内テキスト、注意ボックスにも適用します。

H1 やタイトルに「。」が入る場合も、表示上はそこで改行できる形にします。

悪い例：

```txt
ホイールを替えたい。少し車高を下げたい。吸気音や見た目を変えたい。
```

良い例：

```txt
ホイールを替えたい。
少し車高を下げたい。
吸気音や見た目を変えたい。
```

JSON 上で長い1文字列に詰め込まず、表示上の改行が反映されるブロック構造にします。

### 2-2. 普通の車サイトの口調にする

CBJらしさを優先して、読者に伝わりにくい文章にしません。

普通の車系ガイド記事として自然に読める口調にします。

Goo-net、カーセンサー、KINTO系の実用記事に近い温度感を基準にします。

SNS調、個人ブログ調、美文調、雑誌風に気取りすぎた文体は避けます。

### 2-3. 避ける言い回し

以下は不自然に見えやすいため、必要がない限り使いません。

```txt
〜を見る
〜を整理する
ポイントを見る
〜で見るポイント
視点
判断軸
整合性
本当の理由
先に結論
```

代わりに、普通の車記事として自然な語を使います。

```txt
確認する
比べる
残す
避ける
考える
困りにくい
戻しやすい
説明しやすい
```

### 2-4. 冒頭の作り方

機械的に「結論」から始めません。

読者が実際に困る場面、迷う場面、体感しやすい場面から入ります。

その後で、理由、確認ポイント、判断材料へ進めます。

## 3. 記事構成のルール

### 3-1. 深い内容ほど、見せ方を軽くする

内容を深くするほど、本文を詰め込まないようにします。

スマホで読んだときに、以下の流れで理解できるようにします。

```txt
悩み
↓
理由
↓
確認すること
↓
NG / OK
↓
必要なら画像
↓
行動順
↓
FAQ
```

### 3-2. タイトル下のリードは短くする

タイトル直下に長い本文を置きません。

基本は2文までです。

長い説明は最初のH2本文へ移動します。

### 3-3. マーカーは多用しない

マーカーは1章1つまでを目安にします。

すべてを強調すると、何も目立たなくなります。

本当に読者の判断に効く文だけに使います。

### 3-4. 関連記事は小型カードで出す

関連記事の大型画像を本文中に出しません。

大型画像にすると、記事本体の主題と混ざります。

関連記事は小型カードで、本文の流れを邪魔しない位置に置きます。

---

## 4. 画像のルール

### 4-1. 画像を使う条件

画像は、文章やカード、表だけでは表現しにくい場合に使います。

使うべき例：

```txt
車の部品
エラーコードの例
修理中の工程
構造の違い
センサーや配線の位置
部品同士の関係
実物の見た目を知らないと理解しにくいもの
```

使わない例：

```txt
文字だけで説明できるチェックリスト
順番を説明するだけの流れ
カテゴリ分けだけの内容
雰囲気写真
記事内容と直接関係しない画像
```

### 4-2. 横画像に固定しない

画像は横長に固定しません。

スマホで理解しやすいなら、縦画像を使います。

工程、手順、チェックリスト、比較は縦画像の方が読みやすい場合があります。

### 4-3. 画像は大きく見せる

記事内画像は、中身を大きく見せます。

画像外周に大きな枠や余白がある場合は、可能な範囲でトリミングします。

記事側でも二重枠にならないようにします。

画像表示は以下を基準にします。

```txt
左右に少しだけ余白
本文幅より大きく見せる
画像内の外枠を目立たせない
中身の図解・部品を大きく見せる
キャプションは短くする
```

### 4-4. 画像内の文字

画像内の文字は最小限にします。

大きなタイトル、長文説明、記事タイトル、要約文は入れません。

ラベルや短い項目名だけにします。

一覧画像は完全に文字なしです。

### 4-5. 画像の質感

Guide / Column の画像は、足回り記事の画像を基準にします。

```txt
白〜薄グレー基調
ティール系アクセント
必要なところだけ少量のオレンジ
やわらかい影
スマホで読める文字サイズ
部品はリアル
図解は清潔で実用的
汎用写真や抽象画像は避ける
```

## 5. カード・表のルール

### 5-1. カードデザインは統一する

Guide / Column 記事のカードは、すべて同じ思想で統一します。

新しいカードデザインを記事ごとに増やしません。

共通CSSで表現できる範囲にします。

### 5-2. 表はスマホでは縦カード形式を優先する

スマホで横に詰まる表は使いません。

「項目名 + 説明文」の形で、大きな縦カードとして表示します。

悪い例：

```txt
対象車種｜自分の車の型式や年式に合っているか
取り付け状態｜干渉、固定不良、突出がないか
```

良い例：

```txt
対象車種
自分の車の型式や年式に合っているかを確認します。

取り付け状態
干渉、固定不良、突出がないかを確認します。
```

文字サイズは小さくしません。

添付基準のように、項目名を太字で大きく、説明文も読みやすい大きさにします。

### 5-3. 数字の使い方

01、02 などの数字は、数字をつけた方が見やすくなる場合だけ使います。

対象車種、取り付け状態、最低地上高のように、カテゴリ名だけで分かれていて見やすい場合は数字を振りません。

順序がある場合や、読者が上から追うべき内容は数字を使います。

### 5-4. STEP の使い方

STEP は、段階や手順を説明する場合だけ使います。

順番が重要な作業、修理工程、確認手順、購入前の流れでは使えます。

単なるカテゴリ分けでは使いません。

単なるカテゴリ分けや確認項目の列挙では、STEP表記は不要です。

ただし、順番に進める手順や作業工程を説明する場合は STEP を使ってよいです。

### 5-5. NG / OK 比較

読者に失敗例と良い選び方を見せる場合は、NG / OK を視覚的に分けます。

悪い例と良い例が一瞬で分かるようにします。

```txt
NG
音だけで選ぶ
遮熱を考えない
純正戻しを考えない

OK
熱・雨の影響を確認
センサー位置を確認
純正部品を残す
```

NG は薄い注意色、OK はティール系で分けます。

## 6. Guide / Column 共通レイアウト

Guide / Column 記事は、共通レイアウトCSSを使います。

記事ごとに独自の見た目を増やしません。

使用する基本ブロックは以下です。

```txt
paragraph
marker / highlight
figure
caption
vertical card table
note / callout
related card
FAQ
sources
update history
```

使わないもの：

```txt
BACKGROUNDカード
ISSUE MAP
大型関連記事画像
短文だけの番号カード乱発
本文代わりのカード
雰囲気写真
```

---

## 7. 内部リンクのルール

Guide / Column は孤立させません。

関連するGuide、Column、Cars、Heritageへ自然にリンクします。

ただし、記事本文の途中で大型画像付きカードを出して流れを壊しません。

関連記事は小型カードを基本にします。

---

## 8. 出典・更新履歴

出典と更新履歴は削除しません。

ただし、本文下にURLをベタ出ししてデザインを壊しません。

媒体名、資料名、公式資料名で見せます。

折りたたみ表示を基本にします。

---

## 9. 競合調査と品質基準

Guide / Column を作るときは、同テーマの記事を調査してから作成します。

最低でも5〜10本、重要テーマでは30本を目安に競合を確認します。

低品質な記事は参考にしません。

ただ文字量を増やすだけでは不可です。

検索意図、読者の不安、確認ポイント、画像、FAQ、内部リンクまで含めて勝てる形にします。

公開基準は90点以上です。

85〜89点は保留です。

84点以下は noindex、統合、作り直しを検討します。

---

## 10. 公開前チェック

公開前に必ず以下を確認します。

```txt
句点「。」ごとに改行されているか。
タイトル、リード、本文、FAQ、キャプション、カード内文にも適用されているか。
スマホで読んだときに長文の塊がないか。
タイトル下リードが長すぎないか。
画像は必要な場所だけに入っているか。
画像でしか伝えにくい内容に画像を使っているか。
一覧画像に文字が入っていないか。
画像内の余白や枠で中身が小さくなっていないか。
カード・表は大きく読みやすいか。
数字やSTEPを必要な場面だけに使っているか。
NG / OK の差が一瞬で分かるか。
関連記事が大型画像として本文を邪魔していないか。
出典・更新履歴が残っているか。
Guide / Column 共通CSSの範囲で統一されているか。
```

## 11. 現時点の代表基準

Guide / Column の本文・画像・カード設計は、足回り記事の修正版を基準にします。

基準記事：

```txt
車の足回りが硬い・柔らかいとは？乗り心地の違いと試乗での見分け方
```

ただし、構成を機械的にコピーしません。

文体、画像の役割、スマホでの読みやすさ、カードの使い方を基準として扱います。


## 子Guide展開のルール

- 親Columnに特定車種・特定メーカー・特定部品の事例を大量に詰め込まない。
- 親Columnには代表例を1〜2個だけ入れ、深掘りは子Guideへ分ける。
- 子Guideを後で作る場合は、まず `status: draft` / `publicState: draft` の予定記事として用意してよい。
- 予定記事には、タイトル、狙う検索意図、本文でどこまで深掘りするか、画像をどういう意図で作るかを制作プロンプトとして残す。
- 画像は後で作る。本文構成、挿入位置、画像の役割、キャプションが決まってから生成する。
- 具体例は削らない。重くなる場合は、画像、カード、表、子記事への内部リンクで視認性を補う。
- 特定メーカーや特定車種の事例は、年式・グレード・装備差・店舗判断で変わるため、断定しすぎない。

詳細な子Guide計画は `docs/custom-column-child-guide-plan.md` を参照する。

## 12. 検索で見つけてもらうための非表示設定

Guide / Column 記事では、読者に直接見えにくい項目も必ず確認します。

検索流入やSNS共有、画像検索、Googleの理解に関わるため、本文だけ作って終わりにしません。

必ず設定するもの：

```txt
seoTitle
seoDescription
description
canonicalUrl または自動canonical
heroImage / thumbnail / ogImageUrl
figure画像のalt
Article構造化データ
BreadcrumbList構造化データ
FAQがある場合のFAQ表示崩れ確認
index / noindex 判定
sitemapへの掲載可否
robots設定
内部リンク
更新日と更新理由
出典・参考資料
```

### seoDescription

検索結果で本文の要約として使われる可能性があります。

記事の主語キーワード、読者の悩み、読後に分かることを入れます。

短すぎる説明、抽象的な説明、本文と違う釣り文句は使いません。

### 画像alt

画像の内容を検索エンジンと読み上げ環境へ伝えるために入れます。

「画像1」「図解」だけでは不可です。

画像に写っている内容と、記事内での役割が分かる短文にします。

### OGP / Twitter画像

SNSやリンク共有で表示される画像です。

一覧画像やOG画像には、原則として記事タイトルや長文を入れません。

カード上のタイトル・説明と情報が重複しないようにします。

### canonical

重複URLや似たURLがある場合に、正規URLを検索エンジンへ伝えます。

記事詳細ページでは、公開URLに正しく向いているか確認します。

### 構造化データ

Article と BreadcrumbList は記事ページで必須級として扱います。

FAQ構造化データを入れる場合は、画面に表示されているFAQと内容を一致させます。

### sitemap / robots / indexability

公開記事は sitemap に載る必要があります。

下書き、予定記事、薄い記事、統合予定記事は sitemap に載せません。

noindex と robots のミスは、公開後の流入に直結するため、必ず検証します。

## 13. NG / OK比較カードの標準

Guide / ColumnのNG / OK比較は、今後すべて共通UIを使います。

- NG / OKという文字見出しは大きく出さない。
- NG側は赤系の斜めグラデーションにする。
- OK側は青系の斜めグラデーションにする。
- カード右上内側に大きい赤い×、青い○を置く。
- 丸バッジの中に小さい記号を入れない。
- 記号は背景ではなく、ペンで書いた注釈のような視覚記号として扱う。
- カード本文は短く、句点ごとに改行する。
- 比較UIは本文を補助するために使い、見出しや章分けの代用にしない。
- 章内の小見出しは `subheading` として扱い、比較カードやcalloutにしない。

このUIは、今回のカスタムColumnだけでなく、今後のGuide / Column全体の標準とする。
